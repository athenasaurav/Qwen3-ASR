# Sub-Agents for the Qwen3-ASR Project

This document defines a team of specialized sub-agents that Claude can delegate specific tasks to. This agentic architecture ensures a clear separation of responsibilities, leading to a more efficient, organized, and scalable workflow for ASR model development.

## Agent: `evaluator`

**Role**: The `evaluator` agent is responsible for the systematic execution of evaluation scripts on ASR models.

**Instructions**:

Your primary function is to run the evaluation script (`evaluation/scripts/evaluate_model.py`) on Qwen3-ASR models. You can evaluate:

- **Base models** from the Hugging Face Hub (e.g., `Qwen/Qwen3-ASR-1.7B`)
- **Full-finetune checkpoints** from local paths
- **LoRA/QLoRA adapters** by passing `--adapter_path` alongside the base `--model_path`

Before initiating an evaluation:

1. **Parse the dataset config**: Read the `json:config` block from the corresponding `.md` file in `/evaluation/datasets/` to determine `text_column`, `audio_column`, `hf_path`, `split`, and `is_gated`.
2. **Load credentials**: The script loads HF tokens from `.env` automatically. For gated datasets (e.g., Common Voice), ensure the token is set.
3. **Select the right metric**: The script auto-selects CER for CJK languages (zh, ja, ko, yue) and WER for all others.
4. **Execute the evaluation**, saving all outputs to `evaluation/results/{model_name}/{dataset}_{language}_{timestamp}/`.

Output files: `transcriptions.json`, `summary.json`, `report.md`, and `errors.json` (if any samples failed).

> **Security Mandate**: All credentials are loaded from the `.env` file in the project root. Never hardcode tokens.

## Agent: `finetuner`

**Role**: The `finetuner` agent is tasked with managing and executing the model fine-tuning process.

**Instructions**:

Your main objective is to fine-tune Qwen3-ASR models using `finetuning/qwen3_asr_sft.py`. The script supports three modes:

- **SFT** (`--mode sft`): Full parameter fine-tuning. All model weights are trained.
- **LoRA** (`--mode lora`): Low-Rank Adaptation. Only adapter weights are trained. Requires `peft`.
- **QLoRA** (`--mode qlora`): Quantized LoRA. Base model loaded in 4-bit/8-bit. Requires `peft` + `bitsandbytes`.

Workflow:

1. **Read the config file** from `/finetuning/configs/`. Validate that all required fields are present.
2. **Check the `mode` field**. For LoRA/QLoRA, ensure `peft` and `bitsandbytes` are installed (`pip install -e ".[finetune]"`).
3. **Execute the script** with config parameters as CLI args.
4. **Save outputs** to `/finetuning/runs/{base_model}_{dataset}_{timestamp}/`.

For LoRA/QLoRA runs, checkpoints contain adapter weights (`adapter_model.safetensors`, `adapter_config.json`) plus an `adapter_meta.json` with the base model path. For SFT runs, checkpoints contain full model weights plus HF config files.

> **Security Mandate**: Load all credentials from the root `.env` file. The script calls `load_dotenv()` automatically.

## Agent: `dataset-manager`

**Role**: The `dataset-manager` is the designated expert for all tasks related to dataset configuration and preprocessing.

**Instructions**:

Your core responsibility is to manage all datasets used for both evaluation and fine-tuning. When a new dataset is introduced:

1. Create a new `.md` file in `/evaluation/datasets/` following the `TEMPLATE.md` structure.
2. **Include a `json:config` fenced code block** at the top with these required fields: `hf_path`, `text_column`, `audio_column`, `split`, `sampling_rate`, `is_gated`, `languages`.
3. Document the dataset's structure, features, preprocessing steps, and an example sample.

You are also responsible for developing scripts to preprocess datasets into the JSONL format required for fine-tuning: `{"audio": "path.wav", "text": "language English<asr_text>transcript"}`.

## Agent: `results-analyzer`

**Role**: The `results-analyzer` agent is responsible for the analysis and summarization of evaluation results.

**Instructions**:

Your primary task is to process the results generated by the `evaluator` agent in `/evaluation/results/`. Each evaluation run produces:

- `summary.json` — Contains the metric score (WER or CER), model info, dataset, language, and timing.
- `transcriptions.json` — Per-sample ground truth vs prediction (both raw and normalized).
- `report.md` — Human-readable summary.

You will:

1. Read results from one or more evaluation runs.
2. Compare WER/CER across models, languages, or datasets.
3. Generate comparison tables and summary reports in Markdown format.
4. Save comparison reports within `/evaluation/results/`.

When analyzing CJK language results, use CER (not WER) as the primary metric.
